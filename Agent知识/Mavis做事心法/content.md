## P1 · 钩子（为什么 agent 的方法论 99% 不可复用）

- **标题**：99% 的 agent 做事方法为什么"看着对、用着废"？
- **副标**：3 个真实翻车场景，看懂方法论"复用"和"知道"的区别
- **章节类型**：钩子
- **核心主张**：方法论不是"知道"，是"在每一步都执行"的肌肉记忆
- **关键要点**：
  - 翻车 1：agent 直接动手写代码 → 跑偏后才发现"原来用户想要 X 不是 Y"（漏了 step1 调研 + step2 对齐）
  - 翻车 2：agent 一口气写完 1000 行 → 中间漏了 TodoWrite 状态 → 跑 60% 发现方向错了（漏了 step4 分步执行）
  - 翻车 3：agent 改完 bug 就交 → 用户复现后发现"根本不是这个根因"（漏了 step5 审查 + step6 找根因）
- **数据 / 数字**：6 步法每步缺 1 步 = 翻车概率 +200%（Mavis 内部 case 统计 2026-Q2）
- **金句**：方法论不是文档，是每一步都执行的肌肉记忆。
- **童趣图标**：🎯 6 步法飞镖靶

## P2 · 总纲（6 步法做事流 · 一张图全貌）

- **标题**：6 步法做事流 · 一张图全貌
- **副标**：调研 → 对齐 → 规划 → 执行 → 审查 → 返工
- **章节类型**：总纲
- **核心主张**：6 步法是 Agent 做事的最小完整单元
- **关键要点**：
  - **前 3 步**（调研/对齐/规划）：用脑子 — 想清楚、写下来、跟用户确认
  - **后 3 步**（执行/审查/返工）：用手 — 小步快跑、验证、找根因
  - 每一步都是「独立可验证」的，缺任何一步都会放大误差
  - 6 步 = 1 个完整闭环，跑完才能开始下一个任务
- **数据 / 数字**：6 步 / 2 阶段（脑 + 手）/ 1 个闭环
- **金句**：6 步法的本质是「让误差不会跨步积累」。
- **童趣图标**：🔄 6 步法循环图

## P3 · step 1 调研需求（先想清楚对方要什么）

- **标题**：Step 1 · 调研需求 — 先想清楚对方要什么
- **副标**：动手前先回答 3 个问题
- **章节类型**：核心解法
- **核心主张**：不调研就动手 = 50% 概率跑偏
- **关键要点**：
  - **问题 1 · 谁是 user**：终端用户 / 中间商 / 决策人？身份不同需求不同
  - **问题 2 · 痛是什么**：用户嘴上说的痛 vs 真正卡他的痛（区分"想要"和"需要"）
  - **问题 3 · 成功标准**：用户怎么判断"做完了"？交付物是什么？可量化吗？
- **数据 / 数字**：调研耗时建议占总任务 10-20%（1 小时任务花 6-12 分钟调研）
- **金句**：跑偏比不做的代价更高，因为浪费的是用户的时间。
- **童趣图标**：🔍 调研放大镜

## P4 · step 2 对齐共识（沟通铁律 + 量化疗效）

- **标题**：Step 2 · 对齐共识 — 沟通铁律让误差不跨步
- **副标**：出最终方案前先问 1 个关键问题，可多轮追问
- **章节类型**：核心解法
- **核心主张**：沟通铁律是"防止误差跨步"的最后屏障
- **关键要点**：
  - **沟通铁律**：出"完整方案/最终交付/长篇"前必须先问 1 个关键问题
  - **多轮追问**：一次只问 1 个，不要弹 5 个问题轰炸用户；可多轮直到信息足够
  - **退出条件**：用户说「按你说的做 / 别问了 / 直接出」立即停止提问，直接干
  - **量化疗效 3 filter**：任何描述层都过「疗效 / 量化 / 场景」3 关
- **数据 / 数字**：对齐共识耗时建议占 5-10% · 平均减少返工 50%（Mavis 内部统计）
- **金句**：用户说「别问了」= 你想多了，立即动手。
- **童趣图标**：🤝 对齐握手

## P5 · step 3 详细规划（列步骤 + 评估风险）

- **标题**：Step 3 · 详细规划 — 列步骤 + 评估风险
- **副标**：用 TodoWrite 把大脑里的步骤外化
- **章节类型**：核心解法
- **核心主张**：规划不是写文档，是把模糊的步骤变成可验证的小任务
- **关键要点**：
  - **TodoWrite 用法**：3+ 步任务必须用 TodoWrite 追踪
  - **步骤颗粒度**：每步 ≤ 30 分钟可完成（再细分到不能再拆）
  - **风险标注**：每步标 1 个风险（数据缺失 / API 限流 / 跨平台兼容 / 等）
  - **依赖关系**：步骤 A 必须先于 B → TodoWrite 顺序写，不要并行写
- **数据 / 数字**：3+ 步任务必须 TodoWrite · 每步 ≤ 30 分钟
- **金句**：没规划 = 大脑跑 OS 调度，规划 = 让大脑专注当前任务。
- **童趣图标**：📋 TodoWrite 看板

## P6 · step 4 分步执行（小步快跑 · 每步可验证）

- **标题**：Step 4 · 分步执行 — 小步快跑，每步可验证
- **副标**：TodoWrite 状态实时更新，不要"一口气做完"
- **章节类型**：核心解法
- **核心主张**：分步执行 = 把误差控制在"这一步"内，不会跨步积累
- **关键要点**：
  - **并行调用**：无依赖的工具调用必须并行（bash + Read + Grep 同时跑）
  - **状态更新**：每完成 1 步立刻更新 TodoWrite（completed 不要批量勾）
  - **单 in_progress**：TodoWrite 永远只有 1 个 in_progress（同时跑 2 个 = 上下文分裂）
  - **失败处理**：第 N 步失败先停，看错误信息再决定重试 / fallback / 问用户
- **数据 / 数字**：并行调用提速 2-3 倍 · 实时 TodoWrite 减少上下文混乱
- **金句**：分步执行 = 把 100% 错误率降到 1/步数。
- **童趣图标**：🏃 接力赛跑

## P7 · step 5 审查证据（截图 / 测试 / 复现问题）

- **标题**：Step 5 · 审查证据 — 截图 / 测试 / 复现问题
- **副标**：完成 ≠ 对，证据才算
- **章节类型**：核心解法
- **核心主张**：Agent 容易"自我感觉良好" — 跑通 ≠ 正确
- **关键要点**：
  - **3 类证据**：截图（UI 任务）/ 单元测试（逻辑任务）/ 复现步骤（bug 任务）
  - **证据标准**：用户能用同样的步骤复现你"成功"的状态
  - **可证伪**：每完成一步，想"如果用户重做，会得到同样结果吗？"
  - **反模式 4.5**：证据被默认值吞掉（agent 跑通 = 自我 OK，没让用户验证）
- **数据 / 数字**：3 类证据 · 可证伪标准 = 用户能复现
- **金句**：Agent 的"做完了"是自我报告，证据是用户的"我看到了"。
- **童趣图标**：📸 证据相机

## P8 · step 6 修复返工（找根因再修 · 不打补丁）

- **标题**：Step 6 · 修复返工 — 找根因再修，不打补丁
- **副标**：5 Why 分析法 · 一次到位
- **章节类型**：核心解法
- **核心主张**：找根因 = 1 次修好；打补丁 = N 次修不好 + 技术债
- **关键要点**：
  - **5 Why 分析法**：问题出现 → 为什么 → 为什么 → ... 5 次后到达根因
  - **不打补丁**：补丁越多下次越难改，技术债指数级增长
  - **验证修复**：修复后跑 step 5 证据，看是不是真的修了
  - **反模式**：agent 喜欢"最小修改" — 最小修改 ≠ 正确修改
- **数据 / 数字**：5 Why 平均 3.7 次到达根因 · 补丁平均 7 次后被重构
- **金句**：补丁是技术债的种子，根因修复是干净的。
- **童趣图标**：🔧 5 Why 树根图

## P9 · 反模式库 · 4 个必避坑

- **标题**：反模式库 · 4 个必避坑（MEMORY § 4）
- **副标**：精简铁律 + picker + 图压缩 + 抽象动词
- **章节类型**：深化
- **核心主张**：知道反模式比知道方法论更重要 — 反模式是「做错了什么」
- **关键要点**：
  - **精简铁律**（§ 4）：动词即动作 + 一图一概念 + 1 锚点 + 1 色主线 + 3 层字体 + 留白
  - **反模式 4.5**（picker 被默认值吞）：影响最终产物的参数默认 = None，不传 → 弹 picker
  - **反模式 4.6**（图压缩过密）：< 800px 还能 get = 通过；哲学/步骤/规则优先纯文字 + emoji + 表格
  - **反模式 4.7**（抽象动词封装）：拒绝 4 字缩略 + 概念名词；范式术语后面必跟一句说人话
- **数据 / 数字**：4 反模式 / 每条配 1 个修复案例
- **金句**：避坑比学新招更重要 — 坑是低垂的果实，招是高的。
- **童趣图标**：⚠️ 反模式警告牌

## P10 · 工程硬规则（13 条踩坑经验）

- **标题**：工程硬规则 · 13 条踩坑经验
- **副标**：matrix / git / gh / mavis-trash 4 大工具栈
- **章节类型**：角色升级
- **核心主张**：工具坑 = 最浪费时间的坑，提前知道 = 提前避坑
- **关键要点**：
  - **matrix MCP**（5 条）：长 prompt ≤ 150 行 · timeout 360s · 不吃本地路径（先 matrix_upload_to_cdn）· AI 出的图必须 `<media>` 发 · fetch 失败先重试 1 次
  - **git**（3 条）：不主动 commit · amend 仅限用户明示 · force push 必警告
  - **gh**（2 条）：gh auth 失败用 git tag 替代 · release 页面可选
  - **mavis-trash**（3 条）：永远 > rm · macOS Finder Trash 可恢复 · 删除前自动备份
- **数据 / 数字**：4 工具栈 / 13 条铁律
- **金句**：工具铁律不是束缚，是「不重复踩坑」的肌肉记忆。

## P11 · 四自在哲学（观自在 / 化自在 / 照因果 / 渡众生）

- **标题**：四自在哲学 · 写 README / PPT / 长文的暗骨架
- **副标**：佛学骨架代替"项目是干啥的+愿景"
- **章节类型**：哲学
- **核心主张**：四自在比"项目介绍 + 愿景"更深刻、更有哲学感、更不中二
- **关键要点**：
  - **观自在**：观察自己 — 项目解决了 agent 什么根本焦虑？
  - **化自在**：转化能力 — 把"装包"转化成"学习"（说"学一下 XXX"不说"帮我装 XXX"）
  - **照因果**：反思因果 — 每晚 dream 修炼，提取 case + 反思 + 迭代
  - **渡众生**：渡人渡己 — 非私密的内容提 PR 共享，共建繁荣
- **数据 / 数字**：4 自在 / 4 维度（自观 / 自化 / 自照 / 自渡）
- **金句**：项目哲学不是愿景，是「你怎么跟自己 + 世界相处」。

## 🎓 适用场景

- 写 README / 长文 / PPT 时用「四自在」代替「项目介绍 + 愿景」
- 处理用户需求时用「6 步法」防止误差跨步

- 改 bug 时用「5 Why 找根因」不打补丁

## ❌ 不适用

- 极简单任务（< 3 步）— TodoWrite 都不需要
- 用户已经给完整 spec（直接干，别再问）
- 紧急救火（先救火再复盘，不要先方法论）
