# dream-修炼达尔文自迭代 · pretty-skills 元库自迭代机制

> **一句话定位**：pretty-skills 16 领域所有 case 的长期自迭代引擎 = dream 修炼（每日）+ 达尔文 2.0（每周）+ 人类卡口（永远）

---

## 这个 case 是什么

**作者**：huangrichao2020（设计）+ Mavis（沉淀）· 参考花叔 darwin-skill v2.0（2026-05-22 微软两篇论文）
**生成日期**：2026-07-10
**页数**：10 页（含 9 维评分细则 + 反例黑名单 + human-in-loop 流程）
**所属领域**：玄学修炼

## 核心论点

pretty-skills 沉淀的 30+ case 不能"写完就死"——必须会自我进化。dream 修炼 = 每日 23:00 自动化沉淀新 case；达尔文 2.0 = 每周/每月用 9 维评分 + 多评委 + validation 优化已有 case；human-in-loop = 关键决策永远交回人。3 层缺一不可。

## 适用场景

- pretty-skills 任意 case 的日常维护
- 每月自动跑一遍"哪个 case 落后了"
- 用户在梦境/思考中获得新洞察时沉淀
- skill 之间相互引用 / 知识冲突时裁决

## 双引擎设计

```
pretty-skills 自迭代双引擎
├── 引擎 1 · 每日 dream 修炼（v0 已存在 · 保留）
│   - 每日 23:00 自动化：沉淀当日对话为 3F Content case
│   - 格式：日期 → 沉淀了什么 → 新建/更新了哪些 case → check-3f 结果
│   - 输出：pretty-skills/dream-log.md
│
└── 引擎 2 · 达尔文 2.0 自我优化（v1 新增 · 本 case 核心）
    - 触发：每周日 / 每月 1 日 / 重要 PR 后
    - 9 维评分：3 维借达尔文 2.0 + 6 维 pretty-skills 专属
    - 多评委独立审查（每轮新评委 · 避免锚定）
    - validation-gated 回滚（分数没涨自动回滚）
    - human-in-loop CHECKPOINT（关键决策永远不交 AI）
    - 反例黑名单（8 条踩坑沉淀）
```

## 9 维评分标准（pretty-skills 专属 · 核心）

### 维度 1-3（借达尔文 2.0 · 通用标准）

#### 维度 1 · 失败模式编码
**目的**：skill 必须写清"什么情况下会出错、出错了走哪条分支"

**评分标准**：
- 10 分：明确写出"如果 X 发生就做 Y；否则做 Z"的全部主分支
- 5 分：只有 happy path，错误处理散落各处
- 0 分：完全没有错误处理

**修复指引**：补"失败现象 + 触发条件 + 一线修复 + 仍失败兜底"表

#### 维度 2 · 可执行具体性
**目的**：禁止"建议/可以考虑/视情况而定"等软化措辞

**评分标准**：
- 10 分：每个动作都是具体可执行的命令
- 5 分：少量软化措辞（≤ 2 处）
- 0 分：通篇"建议/可能/灵活把握"（出现 3 处以上扣 3 分）

**禁用措辞清单**：
- 建议 / 可以考虑 / 根据情况 / 灵活把握 / 视情况而定
- 应该 / 可能 / 也许 / 大概

**修复指引**：把所有软化措辞替换为具体命令（"先做 X"而不是"建议先做 X"）

#### 维度 3 · 高风险行动黑名单
**目的**：必须有独立"不要做什么"章节

**评分标准**：
- 10 分：独立章节列出 ≥ 5 条绝对不能做的操作
- 5 分：章节存在但 ≤ 3 条
- 0 分：完全没有"不要做什么"

**修复指引**：补"反例黑名单"章节（参考维度 9 的 8 条通用反例）

### 维度 4-9（pretty-skills 专属 · 元库标准）

#### 维度 4 · 4 件套完整度
**目的**：v3.20 范式 4 件套（content.md + PDF + images/ + 锦绣）

**评分标准**：
- 10 分：4 件套齐全 + check-3f.py EXIT=0
- 5 分：3 件套（缺 1 个）
- 0 分：≤ 2 件套

**修复指引**：跑 `python content-triple-format/check-3f.py <case>`，按错误提示补齐

#### 维度 5 · 锦绣素材完整度
**目的**：v3.1 简化锦绣（2 封面 + 8-12 讲解图 + 融合 md）

**评分标准**：
- 10 分：cover-横屏.png + cover-竖屏.png + slides/8-12 张 + readme.md
- 5 分：3 类素材
- 0 分：≤ 2 类素材

**修复指引**：跑 skill-creator 工具自动生成，或手动补齐

#### 维度 6 · 跨 agent 兼容性
**目的**：5 agent 端都能跑（Mavis / Claude Code / Codex / Cursor / Windsurf）

**评分标准**：
- 10 分：在 5 个 agent 都测试通过
- 5 分：在 3 个 agent 测试通过
- 0 分：只在 1 个 agent 验证

**修复指引**：在 5 agent 端软链 + 各跑一次

#### 维度 7 · 实战验证
**目的**：真用过 + 有疗效数据

**评分标准**：
- 10 分：用户实战验证 + 量化疗效（节省 X 小时 / Y% 提升）
- 5 分：作者自验证
- 0 分：理论推演无实战

**修复指引**：补"疗效段"在 README，含可验证的量化指标

#### 维度 8 · 内容数据支撑
**目的**：每条断言有引用 + 来源 + 可验证

**评分标准**：
- 10 分：所有断言都有引用链接 + 来源可查
- 5 分：关键断言有引用
- 0 分：通篇"我认为/我觉得"

**修复指引**：补"参考"段，引用论文 / 文档 / 数据源

#### 维度 9 · 维护者活跃度
**目的**：最近 30 天有 commit

**评分标准**：
- 10 分：7 天内有 commit
- 5 分：30 天内有 commit
- 0 分：> 90 天无更新

**修复指引**：季度 review 时主动重写 + 提交

## 多评委独立审查协议

### 启动规则

每轮优化启动 2 个独立 AI 评委：
- 评委 A：使用 GPT-4 class 模型
- 评委 B：使用 Claude 3.5 class 模型
- 评委 C（可选）：使用 Gemini Pro class 模型
- 共识：≥ 2 评委分数差 ≤ 1 分 → 共识分数

### 锚定防御

- **不复用**：下一轮启动全新 2 个评委（避免锚定效应）
- **不看历史**：本轮评委不知道上次分数
- **基线公布**：只公布当前 case 内容，不公布基线分数

### 早停机制

- 单轮涨幅 < 1 分 → 早停（避免为凑分堆冗余）
- 干跑模式比例 > 30% → 告警
- 连续 2 轮涨幅 < 0.5 → 强制停手

## 反例黑名单（8 条 · 来自微信文章 + 实战踩坑）

1. **同一个 AI 又改又评**（SkillLens 论文印证 · 单评委准确率 46.4%）
2. **用 `git reset --hard` 当回滚手段**（应该用 `git revert`）
3. **为凑分而往文档里塞冗余**（早停机制防御）
4. **跳过测试提示词直接评分**（必须用真实 case 测试）
5. **一轮内改多个维度**（每轮只改最低维度）
6. **干跑模式比例 > 30%**（必须实测）
7. **静默跳过异常**（任何错误必须显性处理）
8. **忽视维度相关簇**（改一维会带动一簇，要主动识别）

## human-in-loop CHECKPOINT 协议

每个 CHECKPOINT 强制暂停等用户确认：

| 阶段 | CHECKPOINT | 用户决策 |
|---|---|---|
| 阶段 1 · 基线评估 | 🔴 CHECKPOINT 1 | 决定改什么维度 |
| 阶段 2 · 单维度优化 | 🔴 CHECKPOINT 2 | 确认改动方向 |
| 阶段 2.5 · 测试提示词跑（可选）| 🔴 CHECKPOINT 3 | 确认测试结果 |
| 阶段 3 · 回归测试 | 🛑 STOP | 涨幅 < 阈值强制停手 |

## 5 段式优化循环

```
Rollout（跑任务）→ Reflect（复盘）→ Edit（提议改动）→ Validate（验证）→ Apply（应用）
                ↑                                                    ↓
                └────────────────── Reject（回滚） ←──────────────────┘
                                         ↑
                                分数没涨或破坏
```
