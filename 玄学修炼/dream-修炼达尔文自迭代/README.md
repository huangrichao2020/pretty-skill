## 核心论点

pretty-skills 沉淀的 30+ case 不能"写完就死"——必须会自我进化：
- **dream 修炼** = 每日 23:00 自动化沉淀新 case（引擎 1）
- **达尔文 2.0** = 每周/每月用 9 维评分 + 多评委 + validation 优化已有 case（引擎 2）
- **Compaction** = 每月/30天压缩结构（保持轻量）
- **三层自进化** = 每条改动定位到层 + 三问证据链
- **human-in-loop** = 关键决策永远交回人

5 层缺一不可。

## 适用场景

- pretty-skills 任意 case 的日常维护
- 每月自动跑一遍"哪个 case 落后了"
- 用户在梦境/思考中获得新洞察时沉淀
- skill 之间相互引用 / 知识冲突时裁决

## 双引擎设计

```
pretty-skills 自迭代双引擎
├── 引擎 1 · 每日 dream 修炼（v0 已存在 · 保留）
│   - 每日 23:00 自动化：沉淀当日对话为 3F Content case
│   - 格式：日期 → 沉淀了什么 → 新建/更新了哪些 case → check-3f 结果
│   - 输出：pretty-skills/dream-log.md
│
├── 引擎 2 · 达尔文 2.0 自我优化（v1 新增 · 本 case 核心）
│   - 触发：每周日 / 每月 1 日 / 重要 PR 后
│   - 9 维评分：3 维借达尔文 2.0 + 6 维 pretty-skills 专属
│   - 多评委独立审查（每轮新评委 · 避免锚定）
│   - validation-gated 回滚（分数没涨自动回滚）
│   - human-in-loop CHECKPOINT（关键决策永远不交 AI）
│   - 反例黑名单（8 条踩坑沉淀）
│
├── 引擎 3 · Skill 三层自进化（v1.1 新增 · 来源：Datawhale 陈思州）
│   - 路由层 / 指令层 / 资源层 按需加载
│   - 每条改动回答三问：改了哪层 / 解决什么 / 证据是什么
│
└── 引擎 4 · Skill Compaction 定期压缩（v1.1 新增）
    - 触发：每 30 天 / 积累 ≥ 5 条新规则
    - 四问：重复 / 沉睡 / 过重 / 冲突
    - 主文件行数减少目标：≥ 20%
```

## 9 维评分标准（pretty-skills 专属 · 核心）

### 维度 1-3（借达尔文 2.0 · 通用标准）

#### 维度 1 · 失败模式编码
**目的**：skill 必须写清"什么情况下会出错、出错了走哪条分支"

**评分标准**：
- 10 分：明确写出"如果 X 发生就做 Y；否则做 Z"的全部主分支
- 5 分：只有 happy path，错误处理散落各处
- 0 分：完全没有错误处理

**修复指引**：补"失败现象 + 触发条件 + 一线修复 + 仍失败兜底"表

#### 维度 2 · 可执行具体性
**目的**：禁止"建议/可以考虑/视情况而定"等软化措辞

**评分标准**：
- 10 分：每个动作都是具体可执行的命令
- 5 分：少量软化措辞（≤ 2 处）
- 0 分：通篇"建议/可能/灵活把握"（出现 3 处以上扣 3 分）

**禁用措辞清单**：
- 建议 / 可以考虑 / 根据情况 / 灵活把握 / 视情况而定
- 应该 / 可能 / 也许 / 大概

**修复指引**：把所有软化措辞替换为具体命令（"先做 X"而不是"建议先做 X"）

#### 维度 3 · 高风险行动黑名单
**目的**：必须有独立"不要做什么"章节

**评分标准**：
- 10 分：独立章节列出 ≥ 5 条绝对不能做的操作
- 5 分：章节存在但 ≤ 3 条
- 0 分：完全没有"不要做什么"

**修复指引**：补"反例黑名单"章节（参考维度 9 的 8 条通用反例）

### 维度 4-9（pretty-skills 专属 · 元库标准）

#### 维度 4 · 4 件套完整度
**目的**：v3.20 范式 4 件套（content.md + PDF + images/ + 锦绣）

**评分标准**：
- 10 分：4 件套齐全 + check-3f.py EXIT=0
- 5 分：3 件套（缺 1 个）
- 0 分：≤ 2 件套

**修复指引**：跑 `python content-triple-format/check-3f.py <case>`，按错误提示补齐

#### 维度 5 · 锦绣素材完整度
**目的**：v3.1 简化锦绣（2 封面 + 8-12 讲解图 + 融合 md）

**评分标准**：
- 10 分：cover-横屏.png + cover-竖屏.png + slides/8-12 张 + readme.md
- 5 分：3 类素材
- 0 分：≤ 2 类素材

**修复指引**：跑 skill-creator 工具自动生成，或手动补齐

#### 维度 6 · 跨 agent 兼容性
**目的**：5 agent 端都能跑（Mavis / Claude Code / Codex / Cursor / Windsurf）

**评分标准**：
- 10 分：在 5 个 agent 都测试通过
- 5 分：在 3 个 agent 测试通过
- 0 分：只在 1 个 agent 验证

**修复指引**：在 5 agent 端软链 + 各跑一次

#### 维度 7 · 实战验证
**目的**：真用过 + 有疗效数据

**评分标准**：
- 10 分：用户实战验证 + 量化疗效（节省 X 小时 / Y% 提升）
- 5 分：作者自验证
- 0 分：理论推演无实战

**修复指引**：补"疗效段"在 README，含可验证的量化指标

#### 维度 8 · 内容数据支撑
**目的**：每条断言有引用 + 来源 + 可验证

**评分标准**：
- 10 分：所有断言都有引用链接 + 来源可查
- 5 分：关键断言有引用
- 0 分：通篇"我认为/我觉得"

**修复指引**：补"参考"段，引用论文 / 文档 / 数据源

#### 维度 9 · 维护者活跃度
**目的**：最近 30 天有 commit

**评分标准**：
- 10 分：7 天内有 commit
- 5 分：30 天内有 commit
- 0 分：> 90 天无更新

**修复指引**：季度 review 时主动重写 + 提交

## 多评委独立审查协议

### 启动规则

每轮优化启动 2 个独立 AI 评委：
- 评委 A：使用 GPT-4 class 模型
- 评委 B：使用 Claude 3.5 class 模型
- 评委 C（可选）：使用 Gemini Pro class 模型
- 共识：≥ 2 评委分数差 ≤ 1 分 → 共识分数

### 锚定防御

- **不复用**：下一轮启动全新 2 个评委（避免锚定效应）
- **不看历史**：本轮评委不知道上次分数
- **基线公布**：只公布当前 case 内容，不公布基线分数

### 早停机制

- 单轮涨幅 < 1 分 → 早停（避免为凑分堆冗余）
- 干跑模式比例 > 30% → 告警
- 连续 2 轮涨幅 < 0.5 → 强制停手

## Skill 三层自进化（v1.1 新增 · 来源：Datawhale 陈思州）

### 三层按需加载
| 层 | 内容 | 进化方向 |
|---|---|---|
| 路由层 | name / description / 触发边界 | 触发更准确 |
| 指令层 | SKILL.md 正文（任务流程 / 判断标准） | 流程更稳定 |
| 资源层 | references/ / templates / scripts | 场景更丰富 |

### 反馈三问（每条改动必须回答）
1. **改了哪一层？** — 路由层 / 指令层 / 资源层
2. **解决什么问题？** — 什么场景触发了这次修改
3. **用什么结果证明它更好？** — 量化证据 / 用户反馈 / 跑通记录

### Validation 记录格式（每次改动必填）

每条 skill 改动记录在 CHANGELOG.md：

```
### 改动 · YYYY-MM-DD · [case 名]
- **改了哪一层**：路由层 / 指令层 / 资源层
- **触发问题**：什么反馈触发了这次改动
- **改动内容**：引用 diff 行数
- **验证方式**：demo prompt 比对 / 用户实测 / 量化指标
- **结果**：涨分 / 持平 / 降分（降分则 reject 不合并）
```

## Skill Compaction 定期压缩协议（v1.1 新增）

### 什么时候做
- 每 30 天跑一次
- 或积累 ≥ 5 条新规则后主动触发

### 压缩四问
1. **重复**：哪些规则在说同一件事？→ 合并成一条更高层原则
2. **沉睡**：哪些规则长期没被触发？→ 下沉到 references/ 或删除
3. **过重**：主文件是否堆了过多细节？→ 下沉到 references/ 按需读取
4. **冲突**：哪些规则与其他 skill 矛盾？→ 裁决并注明

### 压缩记录格式
```
## Compaction YYYY-MM-DD
- 合并了 N 条重复规则 → [规则描述]
- 下沉了 N 条沉睡规则 → [文件路径 + 触发条件]
- 删除了 N 条冲突规则 → [规则内容 + 原因]
- 主文件行数：XX → YY（减少 ZZ%）
```

## 反例黑名单（8 条 · 来自微信文章 + 实战踩坑）

1. **同一个 AI 又改又评**（SkillLens 论文印证 · 单评委准确率 46.4%）
2. **用 `git reset --hard` 当回滚手段**（应该用 `git revert`）
3. **为凑分而往文档里塞冗余**（早停机制防御）
4. **跳过测试提示词直接评分**（必须用真实 case 测试）
5. **一轮内改多个维度**（每轮只改最低维度）
6. **干跑模式比例 > 30%**（必须实测）
7. **静默跳过异常**（任何错误必须显性处理）
8. **忽视维度相关簇**（改一维会带动一簇，要主动识别）

## human-in-loop CHECKPOINT 协议

每个 CHECKPOINT 强制暂停等用户确认：

| 阶段 | CHECKPOINT | 用户决策 |
|---|---|---|
| 阶段 1 · 基线评估 | 🔴 CHECKPOINT 1 | 决定改什么维度 |
| 阶段 2 · 单维度优化 | 🔴 CHECKPOINT 2 | 确认改动方向 |
| 阶段 2.5 · 测试提示词跑（可选）| 🔴 CHECKPOINT 3 | 确认测试结果 |
| 阶段 3 · 回归测试 | 🛑 STOP | 涨幅 < 阈值强制停手 |

## 5 段式优化循环

```
Rollout（跑任务）→ Reflect（复盘）→ Edit（提议改动）→ Validate（验证）→ Apply（应用）
                ↑                                                    ↓
                └────────────────── Reject（回滚） ←──────────────────┘
                                         ↑
                                分数没涨或破坏
```
